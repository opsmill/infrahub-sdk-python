The client store merge fix comes with four observable behaviour changes. First, the object returned by `get`, `filters` or `all` is a per-query snapshot and is no longer the same Python object as the store entry once that node has been fetched more than once: `client.get(id) is client.store.get(id)` was previously true and is now false after a re-fetch, although the two still compare equal (`==`). The first query to store a node has nothing to merge into, so it still returns the stored object, and so does any query that replaces the entry rather than merging into it. Second, the store hands out living objects: `store.get()` returns the same object across calls, a later query that re-fetches the node updates that object in place, and `RelatedNode.fetch()` caches that store object as the peer. Third, the store replaces the stored entry instead of merging, as every write did before 1.24.0, when the new copy was fetched at a different timestamp (`at`) than the stored one, when the stored node has unsaved local edits on a field the new copy carries, when the new copy was built locally with `client.create()` rather than returned by a query, when the same UUID arrives under a different kind, or when `merge=False` is passed (per query, per `store.set()` call, or globally with `store_merge=False`). Fourth, a successful `save()`, `create()` or `update()` now marks the node's in-memory state as persisted: the saved values count as server state, so later fetches of the same node merge into those fields instead of replacing the node. This does not change what a subsequent mutation sends - an explicitly cleared relationship or an edited peer set is still re-asserted on the next `save()`, exactly as before.
