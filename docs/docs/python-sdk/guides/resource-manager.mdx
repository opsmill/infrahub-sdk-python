The goal of this guide is to show you how to create a resource pool using the Python SDK, and how you can allocated resources with them.

:::note

The guide makes the assumption that we start with an Infrahub instance that doesn't have any data or schema loaded.

:::

## Loading a schema

Save the following schema in a file on your local system. The location or filename are not that important, but in this guide will be using `/tmp/schema.yml`

```yaml
---
version: "1.0"
nodes:
  - name: IPPrefix
    namespace: Ipam
    include_in_menu: false
    inherit_from:
      - "BuiltinIPPrefix"
    description: "IPv4 or IPv6 network"
    label: "IP Prefix"
  - name: IPAddress
    namespace: Ipam
    include_in_menu: false
    inherit_from:
      - "BuiltinIPAddress"
    description: "IP Address"
    label: "IP Address"
  - name: Device
    namespace: Infra
    description: "A Device"
    icon: "mdi:server"
    label: "Device"
    attributes:
      - name: name
        kind: Text
        label: Name
        optional: false
    relationships:
      - name: primary_ip
        label: "Primary IP Address"
        peer: IpamIPAddress
        optional: false
        kind: Attribute
        cardinality: one
```

Load the schema with the `infrahubctl` command.

```shell title="❯ infrahubctl schema load /tmp/schema.yml"
 schema '/tmp/schema.yml' loaded successfully
 1 schema processed in 6.846 seconds.
```

## Creating an IP Prefix object

Next we will be creating an IP Prefix object, which the resource manager will use as a resource to allocate resources from.

  ```python
  await prefix.save()
  ```

## Creating a resource manager

We can now create a resource manager of kind `CoreIPAddressPool`. The kind of the resource manager determines the kind of resource the manager will allocate.

We will create a `CoreIPaddressPool` with the following properties:

- Name: My IP address pool
- Default Address Type: `IpamIPAddress` (the kind of the IP address node defined in our schema)
- Default Prefix Size: 32
- Resources: 10.0.0.0/24
- IP Namespace: Namespace > Default

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  pool = await client.create(
      kind="CoreIPAddressPool",
      name="My IP address pool",
      default_address_type="IpamIPAddress",
      default_prefix_size=32,
      resources=[prefix],
      is_pool=True,
      ip_namespace={"id": "default"}
  )
  await pool.save()
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python

      ip_namespace={"id": "default"}
  )
  pool.save()
  ```

  </TabItem>
</Tabs>

## Allocating a resource out of the pool

We can now start allocating resources out of the `CoreIPAddressPool` we created.

We can use the resource manager to allocate resources out of a pool in 2 different ways:

1. Directly allocate a resource out of a pool. This is typically used when you need to allocate a resource that has no relation to other nodes. For example, allocating an IP address out of a pool that will be assigned to something that is not stored in Infrahub.
2. Allocate a resource out of a pool to a relationship of a node. For example, create a device and allocate an IP address out of a pool and assign it to the device

### Direct allocation of a resource

The Python SDK provides 2 methods that perform direct allocations:

- `allocate_next_ip_address` to allocate resources out of `CoreIPAddressPool` pools
- `allocate_next_ip_prefix` to allocated resources out of `CoreIPPrefixPool` pools

We will use `allocate_next_ip_address` to allocated an IP address out of the `CoreIPAddressPool` we created.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  ip_address = await client.allocate_next_ip_address(
      resource_pool=pool,
      data={"description": "my first allocated ip"}
  )
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  ip_address = client.allocate_next_ip_address(
      resource_pool=pool,
      data={"description": "my first allocated ip"}
  )
  ```

  </TabItem>
</Tabs>

We provided a data argument to method. This data argument is used to pass attributes and relationships that we want to set on the allocated resource. In this case we are setting to the description of the allocated IP Address.

You can allocate resources in an idempotent way by passing an identifier argument to the allocation method. This identifier links the resource pool with the allocated resource allowing us to create idempotent allocation behavior. This is crucial when you want to allocate resources in an idempotent way using [generators](https://docs.infrahub.app/topics/generator).

In this example we are executing the `allocate_next_ip_address` method 2 times, using the same identifier.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  ip_address2 = await client.allocate_next_ip_address(resource_pool=pool, identifier="my-allocated-ip")
  ip_address3 = await client.allocate_next_ip_address(resource_pool=pool, identifier="my-allocated-ip")

  assert ip_address2.id == ip_address3.id
  assert ip_address2.address.value == ip_address3.address.value
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  ip_address2 = client.allocate_next_ip_address(resource_pool=pool, identifier="my-allocated-ip")
  ip_address3 = client.allocate_next_ip_address(resource_pool=pool, identifier="my-allocated-ip")

  assert ip_address2.id == ip_address3.id
  assert ip_address2.address.value == ip_address3.address.value
  ```

  </TabItem>
</Tabs>

### Allocating resources to a relationship of a node

Another way we can use resource managers is in situations where we create a node that has a relationship and we want to use a resource manager to allocate a new resource for that relationship. For example, we want to create a new device (or server) and assign an IP address to the device out of a pool.

The Python SDK allows you to set the relationship of a Node to the resource pool that you want to allocate from. The resource will be allocated when you `save` the node.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  device = await client.create(kind="InfraDevice", name="dev-123", primary_ip=pool)
  await device.save()
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  device = client.create(kind="InfraDevice", name="dev-123", primary_ip=pool)
  device.save()
  ```

  </TabItem>
</Tabs>

When you allocated to a relationship of a node, the resource allocation happens in an idempotent way. An identifier is automatically assigned to the resource allocation in this case.

## Branch agnostic resource allocation

Resource managers have to allocate resources in a branch agnostic way. For example if we allocate a resource in a branch, then that resource should also be allocated in the main branch, even if the resource object does not yet exist in the main branch.

Without this behavior we could allocate the resource multiple times, which should not be possible.

Create a branch named `test`

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  await client.branch.create("test")
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  client.branch.create("test")
  ```

  </TabItem>
</Tabs>

Allocate a new IP address in the `test` branch.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  ip_address4 = await client.allocate_next_ip_address(
     resource_pool=pool,
     branch="test"
  )
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  ip_address4 = client.allocate_next_ip_address(
      resource_pool=pool,
      branch="test"
  )
  ```

  </TabItem>
</Tabs>

Currently there is no dedicated functionality in the Python SDK to do this, so for now we have to use a GraphQL query.

```graphql
query {
  InfrahubResourcePoolAllocated(pool_id: "<id of the pool>", resource_id: "<id of the prefix>") {
    edges {
      node {
        display_label
        branch
      }
    }
  }
  IpamIPAddress {
    edges {
      node {
        display_label
      }
    }
  }
}
```

Notice that we have one IP address allocated by the Resource manager in the test branch. The query in the main branch shows us this allocation, indicating that it has been allocated and the resource cannot be allocated again. However, the IP address does not exist itself within the main branch.

## Create a number pool with ranges

A number pool allocates from its ranges. Pass `ranges` as a list of dictionaries with `start`, `end` and `allocation_weight`. A range without a `start` or an `end` is open on that side, and ranges with a higher `allocation_weight` are allocated from first. Without `ranges`, the pool has one range with no start and no end.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  pool = await client.create(
      kind="CoreNumberPool",
      name="VLAN IDs",
      node="InfraVLAN",
      node_attribute="vlan_id",
      ranges=[
          {"start": 100, "end": 199, "allocation_weight": 10},
          {"start": 200, "end": 2999},
      ],
  )
  await pool.save()
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  pool = client.create(
      kind="CoreNumberPool",
      name="VLAN IDs",
      node="InfraVLAN",
      node_attribute="vlan_id",
      ranges=[
          {"start": 100, "end": 199, "allocation_weight": 10},
          {"start": 200, "end": 2999},
      ],
  )
  pool.save()
  ```

  </TabItem>
</Tabs>

The declared list is the complete set of ranges. Saving the same pool with `allow_upsert=True` sets the ranges of an existing pool to that list: Infrahub keeps the ranges whose bounds match, creates the new ones and deletes the others.

To add, change or delete a single range of an existing pool, work with its `CoreNumberPoolRange` node. Infrahub refuses changes made through the pool's `ranges` relationship with `add()` or `remove()`, because the pool takes its ranges as bounds, not as references to range nodes.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  # Add a range
  new_range = await client.create(kind="CoreNumberPoolRange", start=3000, end=3999, pool=pool)
  await new_range.save()

  # Change its weight
  new_range.allocation_weight.value = 50
  await new_range.save()

  # Delete it
  await new_range.delete()
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  # Add a range
  new_range = client.create(kind="CoreNumberPoolRange", start=3000, end=3999, pool=pool)
  new_range.save()

  # Change its weight
  new_range.allocation_weight.value = 50
  new_range.save()

  # Delete it
  new_range.delete()
  ```

  </TabItem>
</Tabs>

Infrahub refuses a range that overlaps another range of the pool, and refuses a change or a deletion that would leave a number the pool tracks outside every range. The ranges of a pool generated from a schema attribute are set in the attribute's `parameters.ranges` instead, and cannot be changed through `CoreNumberPoolRange` nodes.

## CoreNumberPool and attribute allocation

`CoreNumberPool` allocates integer values (such as VLAN IDs or AS numbers) directly to node attributes. The pool assigns the integer value at the moment the node is created on the server.

```python
vlan = await client.create(
    kind="InfraVLAN",
    name="VLAN-100",
    vlan_id={"from_pool": {"id": pool_id}},
)
await vlan.save()
```

### Attach a number you choose to a pool

To keep a number you choose and have the pool track it, pass both `value` and `from_pool`. The pool records the number as one a user provided, and does not allocate a new one.

### Detach a number from its pool

Call `detach_from_pool()` on the attribute. The attribute keeps its number, and the pool stops tracking it when the node is saved.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  vlan = await client.get(kind="InfraVLAN", name__value="VLAN-200")
  vlan.vlan_id.detach_from_pool()
  await vlan.save()
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  vlan = client.get(kind="InfraVLAN", name__value="VLAN-200")
  vlan.vlan_id.detach_from_pool()
  vlan.save()
  ```

  </TabItem>
</Tabs>

To find which pool tracks a number on a node you fetched, query the node with `property=True` and read the attribute's `source`, which is the number pool.

### Limitation: `allow_upsert=True` with a pool-sourced HFID attribute

`CoreNumberPool` assigns the integer value at server creation time, and a new value on each creation. When a node's human-friendly identifier (HFID) includes a pool-sourced attribute, the HFID is never stable, so an upsert can never match an existing node by it. Rather than updating, each `save(allow_upsert=True)` would create another node. The SDK blocks this up front to avoid silently duplicating data.

:::warning

Calling `save(allow_upsert=True)` on a node whose HFID contains a `CoreNumberPool`-sourced attribute raises `ValidationError` before any network call is made.

```python
# Schema has human_friendly_id: ["vlan_id__value"]
vlan = await client.create(
    kind="InfraVLAN",
    name="VLAN-100",
    vlan_id={"from_pool": {"id": pool_id}},
)

# This raises ValidationError - vlan_id is pool-sourced and in the HFID, so the upsert can't be idempotent
await vlan.save(allow_upsert=True)
```

**Alternatives:**

- **Look up and reuse** - find the existing node by a stable attribute or relationship and reuse it, otherwise create it once. This is the idempotent pattern to use in generators:

  ```python
  existing = await client.filters(kind="InfraVLAN", service__ids=[service.id])
  vlan = existing[0] if existing else await client.create(
      kind="InfraVLAN",
      name="VLAN-100",
      vlan_id={"from_pool": {"id": pool_id}},
  )
  await vlan.save()           # creates on first run, pool assigns vlan_id; reuses afterwards
  ```

- **Explicit id** - if you already know the node's UUID, set `node.id` before saving. The upsert will use the UUID directly and skip HFID lookup:

  ```python
  vlan.id = "known-uuid"
  await vlan.save(allow_upsert=True)  # matches on the id directly, no HFID lookup needed
  ```

- **Deterministic identifier** - if possible, design your schema so the HFID uses a non-pool attribute (for example, a human-assigned `name`) and keep `vlan_id` out of the HFID.

:::
