# Using the client store

The client in the SDK contains a store that is used to store objects in a local cache.

The store is mainly used for the internal working of the SDK. It is used to create relations between objects that might not yet exist in the database, or to store relations for objects that were retrieved from the database, amongst other things.

The store stores objects that we are retrieving from Infrahub using the different query methods. This allows to not have to keep references to objects throughout scripts, or avoids situations where we have to re-execute queries.

## What the store guarantees

The store keeps, per field, the freshest value the SDK has seen. Re-querying a node merges the new data into the stored node; it does not replace the cached node wholesale. The store is a per-field freshness cache, not a point-in-time snapshot: a single stored node can hold data collected by several queries.

:::warning Behaviour change in version 1.24.0

Before SDK 1.24.0, every query fully replaced the stored node, so a shallow re-fetch could silently drop attributes or relationships that an earlier, deeper query had loaded. Since 1.24.0 the store merges instead. See [forcing a clean replace](#forcing-a-clean-replace) to restore the previous behaviour.

:::

The merge works field by field, for attributes and relationships alike:

- A field that was part of the query overwrites the stored value, even when the new value is empty or `None`. A relationship cleared on the server, or an attribute set back to `None`, is reflected after a re-fetch that includes it.
- A field that was not part of the query keeps its stored value. Fetching a node with a subset of its attributes never erases what an earlier query loaded.
- A re-fetched relationship of cardinality many replaces its full member list, so a peer removed on the server is dropped from the store.

This makes re-collecting the same information safe and idempotent: it refreshes what you fetched and never drops what you did not.

Consider a deep fetch followed by a shallow one:

### When the store replaces instead of merging

In the following cases, the store drops the stored entry and keeps the new copy instead, which is what every write did before 1.24.0:

- The two copies were fetched at different timestamps. See [historical queries and the store](#historical-queries-and-the-store).
- The stored node has unsaved local edits (an attribute you changed, a relationship you assigned, or peers you added or removed) and the new copy carries one of those fields. The new copy reflects the server, and your edited object stays in your hands but leaves the store. Save the object, or drop its reference, before fetching it again if you want the store to keep a single object for it.
- The new copy was built locally with `client.create()` rather than returned by a query, for example when `save(allow_upsert=True)` lands on a node that is already stored. The saved object becomes the stored entry.
- The same UUID arrives under a different node kind.
- You asked for a replace with `merge=False`. See [forcing a clean replace](#forcing-a-clean-replace).

References handed out before a replace keep pointing at the old object and stop receiving updates.

### Returned objects compared to stored objects

Queries hand you what you asked for; the store remembers the merged view of every field it has fetched. The object returned by `get`, `filters` or `all` reflects only that query, while `store.get()` returns the merged view, so the two can differ once the same node has been fetched more than once. They compare equal (`==`, equality is based on the node id) but they are not the same Python object (`is`).

The first query to store a node is the exception: with nothing to merge into, the store keeps that very object, so the returned object and `store.get()` are the same object until the next fetch of that node.

Merged does not mean cumulative. A field the newer query fetched overwrites the stored value, even to `None`, and a cardinality-many relationship takes the fetched member list wholesale, so a peer removed on the server disappears from the store. Only fields the newer query did not ask for keep their previous value.

### The store hands out living objects

The store keeps one object per node and mutates it in place when new data arrives. Every `store.get()` call for the same node returns the same object, and a later query that re-fetches the node refreshes the object that earlier references already point at. If you need a snapshot that does not change under you, keep the object returned by the query instead of the store copy.

A relationship peer resolved with `fetch()` is the store object, so `.peer` and `store.get()` return the same object afterwards. Assigning a peer directly caches exactly the object you assigned: assigning the result of `store.get()` keeps the live store object, while assigning a per-query result does not.

### Staleness caveat

A merged value is only as fresh as the last query that fetched it. The store does not track when each individual field was fetched: it always represents the latest data seen per branch.

## Retrieving objects from the store

You can retrieve objects from the store using their `id` or `hfid`. When using the `hfid`, we also have to provide the `kind` of the object that we want to retrieve.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  tag = await client.get("BuiltinTag", name__value="BLACK")
  tag_in_store = client.store.get(key=tag.id)
  tag == tag_in_store
  
  tag = await client.get("BuiltinTag", name__value="BLACK")
  tag_in_store = client.store.get(key=tag.hfid, kind="BuiltinTag")
  tag == tag_in_store
  ```

  </TabItem>

## Manually storing objects in the store

You can store objects in the store manually using the `set` method. This has the advantage that you can choose a key that you want to use to reference the object in the store, besides the `id` or `hfid`. For example, we could use the name attribute value of the node as the key.

Like the query methods, `set` merges by default: if a node with the same `id` is already in the store, the object you pass is merged into the existing entry instead of replacing it. Pass `merge=False` to store the object verbatim and drop what the store previously knew about that node.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  tag = await client.get(kind="BuiltinTag", name__value="RED", populate_store=False)
  client.store.set(key=tag.name.value, node=tag)
  
  tag_in_store = client.store.get(key=tag.name.value)
  tag_in_store = client.store.get(key=tag.id)
  tag_in_store = client.store.get(key=tag.hfid, kind="BuiltinTag")
  ```

  </TabItem>
  <TabItem value="Sync" default>


## Forcing a clean replace

A merge can never *forget* a field that was cached earlier but not re-fetched. For example, to observe that a relationship no longer exists when your refresh query did not select it, the merged entry is not enough. For those cases you can force a clean replace, which drops all prior knowledge of the node and stores exactly what the query fetched.

The replace behaviour is available at three levels:

- Per query, with the `merge` argument on `get`, `filters` and `all`.
- Per store write, with the `merge` argument on `store.set()`.
- Globally, with the `store_merge` configuration option (or the `INFRAHUB_STORE_MERGE` environment variable), which restores the pre-1.24.0 replace-everything behaviour for the whole client.

<Tabs groupId="async-sync">
  <TabItem value="Async" default>

  ```python
  # Per query
  tag = await client.get(kind="BuiltinTag", name__value="RED", merge=False)

  # Per store write
  client.store.set(node=tag, merge=False)

  # Globally
  client = InfrahubClient(config=Config(store_merge=False))
  ```

  </TabItem>
  <TabItem value="Sync" default>

  ```python
  # Per query
  tag = client.get(kind="BuiltinTag", name__value="RED", merge=False)

  # Per store write
  client.store.set(node=tag, merge=False)

  # Globally
  client = InfrahubClientSync(config=Config(store_merge=False))
  ```

  </TabItem>
</Tabs>

## Historical queries and the store

The store records the timestamp each node was fetched at: live data, or the `at` passed to the query. Only copies fetched at the same timestamp merge. When a node arrives from a different timestamp than the stored copy (a historical query after a live one, a live query after a historical one, or two different `at` values), it replaces the stored entry, so a single stored node never blends data from two points in time. `node.save()` carries live data, so a saved node replaces a copy that was fetched at a point in time.

Every query still populates the store, whatever its `at`, so relationship peers resolve through `.peer` as they did before 1.24.0. The store holds one copy per node, though: whichever timestamp wrote a node last is the one the store returns. If a script needs live and historical views of the same nodes side by side, use a dedicated client for each timestamp (`client.clone()`), or pass `populate_store=False` on the queries that should not touch the store.

Compute the `at` timestamp once and reuse it. A relative timestamp rebuilt for every call is a slightly different instant each time, so each query replaces what the previous one stored instead of merging with it.

Fetching the peers of a historical node with `fetch()` runs a live query: it does not reuse the `at` of the node the relationship belongs to.

## Disable storing objects in the store using the different query methods

In some scenarios it might not be desirable to automatically store the retrieved objects in the store, when using the SDK client's different query methods. In this case you can set the `populate_store` argument to `False`.
