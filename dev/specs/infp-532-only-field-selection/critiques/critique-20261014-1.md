# Critique Report: Fetch Only the Named Fields with `only`

**Date**: 2026-10-14
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The spec carries every requirement, journey, edge case, success criterion and scope limit of the idea brief, and adds nothing the brief excludes. The plan's design (a separate query path for `only`, a per-field "the response contained this field" record, a marker on nodes from `only`, and private reads for the SDK's own operations) is sound and keeps default, `include` and `exclude` queries unchanged. Its code references are accurate. The claim in R8 holds: tracing `save()`, `create(allow_upsert=True)`, `update()`, `_generate_input_data`, `_strip_unmodified`, `_generate_mutation_query`, `_process_mutation_result`, `get_human_friendly_id`, `store.set`, `__repr__`, `__eq__`/`__hash__` and batch create found no read of an unloaded field outside the R8 list, given the four details in E5. No conflict with the constitution was found.

Three problems block tasks. E1 and E2 were confirmed with a script run against this tree; E3 follows from the order of steps that R10 states.

- E1: peers of relationships that exist only on an implementing kind are never built. For generic kinds, this breaks FR-004 and FR-005.
- E2: `fetch()` on `ancestors` and `descendants` raises `ValueError` when they are not loaded, which they are not under FR-006.
- E3: the reload in `RelationshipManager.fetch(only=...)` sends a data query before the name check, which SC-004 forbids.

All three can be fixed by editing research.md and the contract; none needs a new design. The other findings are wording fixes in the spec, implementation details the tasks need, extra tests, and two questions for the owner.
