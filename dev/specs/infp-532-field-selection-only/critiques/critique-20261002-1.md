## Executive Summary

The spec and plan are in good shape. The problem is real and measured (`infrahub-sync` validation, generator timeouts). The scope is carved deliberately, and the two-step release (warn in 1.x, raise in 2.0) puts the breaking change on the constitution's standard path. The design keeps the async/sync paths on shared decision helpers and evaluates the known-state rule at read time, which removes a whole class of save-path bookkeeping.

Three issues must be fixed before tasks are generated:

1. Removing `hfid` from the default query envelope is **observable**. `InfrahubNode.get_raw_graphql_data()` returns the raw payload, the Ansible collection's `node` module hands that payload to playbooks, and `infrahubctl export` writes it to disk. The "nothing reads it" premise behind FR-017 and SC-004 is wrong for code that never opts in.
2. FR-026's "point at peer hydration" case can't occur as specified. Under the plan's store rule (R10), floor-only peers are never stored, so the common mistake (`node.site.peer.name.value` after `only=["site"]`) fails in `RelatedNode.get()` with a store-lookup `NodeNotFoundError`, not with a field read.
3. FR-020 says assignment "always succeeds", which literally contradicts the existing `UninitializedError` guard on cardinality-many writes that the plan deliberately keeps (R15).

The remaining findings are clarifications and test-planning improvements.
